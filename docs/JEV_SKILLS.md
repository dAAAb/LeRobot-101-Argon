# 動作指令、可組合技能與 Jev

更新：2026-09-23。文字搜尋先理解使用者想找物件或做動作；動作要求成為第一張推薦卡，點選後才由 Astra 規劃、本機程式逐步執行與核對。Jev 可參與文字分類及候選動作排序。目前沒有訓練新的馬達動作模型，也沒有因此確認抓取或完整揮手已在實機成功。

## 如何使用

首頁只有「LeRobot 搜尋」與「好手氣」兩個主按鈕。在搜尋框輸入「先抬高1公分，再揮揮手」，按 Enter 或搜尋，畫面先顯示「正在理解你的搜尋」，再把動作建議放在最上方。**此時不讀相機、不連馬達，也不執行建議動作**；點選推薦卡的動作按鈕，才開始取得新的腕部證據、規劃與執行。按鈕使用該張卡片保存的原始指令，不會改用其後在搜尋框編輯的文字。

物件名稱如「白色圓筒」沿用原有環顧與辨識流程。不支援的動作（例如指定位置堆疊）或意思不明的文字，仍以搜尋結果解釋原因，沒有執行按鈕。停止或沒有即時腕部影像時仍可產生文字建議；真正執行時必須恢復手臂並有可用影像。上傳照片、點選預覽、查看物件與好手氣保持原有用途。

介面顯示規劃、執行與核對階段，並列出每個計畫步驟。只有對應技能的完成條件通過，該步才顯示「已驗證」；全部步驟都通過，整項指令才顯示完成。受阻時保留已驗證的進展，不執行後續步驟；不支援的指令顯示原因，不偷偷改做其中一部分。

- `POST /api/search`：一般純文字搜尋先做語意分類，初始工作階段為 `understanding`。動作或模糊要求完成後保留 `kind="search"`、`result=null`，新增 `action_suggestion`；物件要求則繼續既有搜尋流程。
- `action_suggestion`：包含 `kind`（`action` 或 `ambiguous`）、`query`、`instruction`、`title`、`summary`、`label`、`availability` 及 `reason`。只有 `action` 且 `availability` 為 `available`／`experimental` 可顯示執行按鈕；`unsupported`／`clarify` 只說明原因。
- `POST /api/command`：推薦卡點選後接受 `{"instruction":"先抬高1公分，再揮揮手"}`，長度 1–500 字，回傳一般 `kind="command"` 工作。
- `GET /api/jobs/{id}`：沿用工作輪詢。指令回報放在 `command_result`，搜尋用的 `result` 不會被當成指令結果。
- `GET /api/skills`：回傳技能目錄、限制、信心門檻及不含金鑰的 Jev 狀態。
- `GET /api/status`：包含 `capabilities.command` 與可選提供者的 `tactics` 狀態。

POST 沿用本機工作授權與單一工作控制；逾時不會自動重送可能已受理的動作。停止、持物狀態與每個技能的執行條件由控制器檢查。持物時仍可輸入「放開」，但必須通過既有支撐與釋放檢查。

伺服器剛啟動時，指令先確認影像可用與未取消，再以唯讀連線建立馬達通訊，才擷取配對關節姿態的腕部影像。真正的移動技能會先採用馬達既有的保持目標，再提出局部路徑；不因冷啟動而重新啟用扭力或重寫保持目標。單純產生推薦卡不走這些步驟。

## 誰負責什麼

| 層 | 輸入與輸出 | 權限 |
| --- | --- | --- |
| Jev／Astra 搜尋語意分類 | 使用者文字、技能目錄 → 物件搜尋、動作建議或待釐清 | 不接收影像，不讀馬達，不產生可直接執行的計畫；Jev 無結果時交給 Astra |
| Astra 指令規劃 | 使用者指令、技能目錄與新的腕部影像 → 具型別的有限步驟 | 描述要嘗試的工作；計畫本身不授權移動 |
| Astra 每步視覺判斷 | 當前腕部影像、這一步的候選路徑 → 空爪、人員與物件淨空等判斷 | 可阻擋缺少必要證據的動作；不產生任意馬達值 |
| Jev 候選排序 | 精簡語意 JSON、已通過檢查的選項 → 一個候選 ID 或放棄 | 只在現有合格候選中表示偏好，不能新增候選或變更路徑 |
| 本機技能與控制器 | 已核對的技能參數 → 受限關節動作、實測位置與驗證回報 | 保有停止、行程、桌面模型、相機、追蹤及回饋檢查 |

正式感知仍只使用指定腕部相機。D435 供開發者獨立旁觀、記錄與驗證實際動作，不進入終端用戶流程、正式 Astra／Jev 決策或腕部立體估算；拔除 D435 不影響產品所需的資料來源。Astra 與 Jev 都透過雲端服務推論，本機負責感知前處理、控制與狀態保存。

TypeSafe 將 Jev 定義為對狀態回答結構化問題的模型；它接受文字與 JSON，**不接受圖片、聲音或影片**。因此不能把腕部影像直接交給 Jev 取代視覺辨識。[官方介紹](https://docs.typesafe.ai/introduction)、[State 格式與輸入限制](https://docs.typesafe.ai/concepts/state)。

技能目前是可重用的程式與回饋控制器，不是從示範資料學成的馬達政策。官方也說明 Jev 不為客戶資料做 fine-tuning 或 LoRA；本次整合沒有更動其權重。[官方模型說明](https://docs.typesafe.ai/models)。

## 技能目錄與限制

「已實作」表示流程及完成條件已存在，不表示任意姿勢、任意物件都已通過實機驗證。

| 技能 | 分類 | 完成條件及限制 |
| --- | --- | --- |
| `observe` 看一看 | 已實作 | 取得這次腕部影像與辨識結果；完成觀察不代表已找到或拿起目標 |
| `move` 移動手臂 | 已實作 | 指定方向與距離，拆成短步，重新觀察並回報累積實測進展；未到指定範圍就不完成該技能 |
| `open` 張開空夾爪 | 已實作 | 先確認空爪與張開路徑，再核對馬達回饋；持物時不能用它代替釋放 |
| `release` 放開 | 已實作 | 沿既有受控流程釋放已有支撐的物件，並驗證空爪；不是搬運、丟下或指定位置放置 |
| `wave` 揮手 | 實驗 | 可先抬高或退讓；只有完整手勢驗證通過才完成，抬手本身不算揮手成功 |
| `grasp` 抓取 | 實驗 | 指定目標、逐步對準、輕合與離桌驗證；夾爪閉合不能代替抓取成功 |
| `place` 放到指定位置 | 未開放 | 指定位置搬運與穩定放置尚未驗證 |
| `stack` 堆疊 | 未開放 | 放置位置、高度與穩定性尚未驗證 |

一份計畫最多 8 個步驟，單個明確移動步驟為 1–30 mm，計畫明確要求的移動總量最多 60 mm。執行器再把移動拆成最多 5 mm 的局部步驟；每個移動技能最多 16 次局部嘗試。揮手內部重新定位有它自己的既有範圍與次數限制，不因計畫通過而取消。不能組合 `grasp + move + release` 冒充尚未提供的 `place` 或 `stack`。

## Jev 的實際接點

純文字搜尋先向 Jev 提出一次語意選擇：物件搜尋、已實作動作、實驗動作、不支援動作或待釐清。選项描述與技能目錄固定由本機程式提供，使用者原文只是要理解的資料。這一步沒有影像或當前淨空判斷，不以關鍵字規則冒充語意辨識。Jev 缺少設定、放棄、低信心、逾時或錯誤時，由同一套 Codex Astra 的純文字 JSON schema 推論接手；兩者都無法完成時回報失敗，不把未知要求直接送去移動。

Jev 也接在揮手的退讓選擇處。**這類實體動作排序**必須先有多個通過當次視覺與幾何檢查的候選，才有排序工作可做。沒有合格候選時不呼叫它求一個肯定答案；只有一個合格候選時也不需要額外推論。

一次揮手的 Jev 選擇呼叫上限為 12 次，沒有背景高速循環；選定退讓方向後仍鎖定方向。候選與當前狀態會重新取得，先前判斷不授權未來步驟。Jev 放棄、低信心、逾時或錯誤時，回到原有「合格候選依當次視覺信心排序」的選法，不擴大動作權限，也不解除阻擋。

`server/jev.py` 使用官方 `POST https://api.typesafe.ai/v1/systemone`，模型預設 `jev-latest`，提出一個 `Choice` 問題 `next_skill`。候選固定在請求內，另加 `abstain`。回應的候選 ID、完整機率鍵集合、有限數值、機率總和、最高機率選項及型別都會檢查。[官方 HTTP API](https://docs.typesafe.ai/api)。

本機介面是 `JevPolicy(...).choose(state, candidates, cancel=...)`。預設等待上限 3 秒，一次只保留一個在途請求；晚到或取消後的答案不採用。沒有自動重試，請求大小限制 16 KiB，最多 32 個技能候選。狀態欄位排除原始影像、馬達目標及程式碼，回傳內容沒有可直接執行的程式或馬達值。診斷只保存固定錯誤代碼，不保存提供者錯誤正文或驗證標頭。

Jev 選項分布的 `confidence` 與某一選項的 `probability` 是不同欄位；本機排序預設採用門檻為 0.5。它們都不是避免碰撞的機率，也不能取代實際淨空條件。[官方 Confidence 說明](https://docs.typesafe.ai/confidence)。

## 動作接收與部分進展

目前視覺接收門檻分開設定：局部移動 0.7、揮手 0.8、接觸／輕合與抓取驗證 0.9。每個動作仍須同時滿足自己的明確條件；單靠分數高不會通過阻擋。

空手局部移動允許誠實回報「有用但未到原目標」的進展。例如要求 3 mm，實測沿要求方向約 1.5 mm，只在空爪已確認、位置停穩、仍在已檢查範圍、方向與姿態誤差合格且離目標更近時，才可以結束這一小步並重新觀察。控制器仍要求連續三個合格穩定樣本；沒有因此增加馬達輸出或無進展重試次數。

空手揮手的單肘抬高另外啟用短暫的「等馬達反應」：第四次位置校正後，如果尚未看到 3 ticks 的有效進展，保留既有目標，最多觀察到該次寫入後 0.5 秒。這段期間不發第五次校正，位置、相機、溫度、取消與反向超越檢查照常執行，也不延長原本 3 秒總期限；只有足夠的實測進展才回到原有流程，否則停止。此選項預設關閉，只由空手 `elbow_raise` 路徑開啟，不套用到 Cartesian 精細抓取，也不更動 gain、補償上限、輸出或 EEPROM。

`partial_progress` 不是任務成功，也不是已抓住、已抬起物件或精確到位。指令中的移動技能還要累積實測進展、核對剩餘距離；未完成前不會跳到下一個計畫步驟。持物與抓取驗證不因這個空手接收條件而放寬。位移來自編碼器與機構模型，仍不是外部量測確認的毫米精度。

9 月 23 日實機抬手遇到一次 `wrist_flex` 回應逾時，新增有界的串列讀取重試。本機安裝的 `scservo_sdk/scservo_def.py` 定義 `COMM_RX_TIMEOUT=-6`（未收到回應）與 `COMM_RX_CORRUPT=-7`（回應封包損壞）。只有這兩種通訊結果且沒有 servo error 時，才在同一串列鎖內最多讀取 3 次，每次重試前等待 4 ms 並清除 RX 緩衝，再送同一 register 的 READ。SDK 的 `clearPort()` 實際只呼叫 TX `flush()`，因此本機明確呼叫 `reset_input_buffer()`；不更動 SDK。此協定沒有請求序號或回覆中的 register 標籤，清緩衝不能證明任何晚到封包的絕對新鮮度，仍依原有停穩與回饋檢查判斷。

這項修正不重送寫入、不重試馬達保護錯誤，也不把持續失聯視為成功。夾爪接觸 telemetry 保持整組 fail-fast：任一 register 讀取失敗就丟棄該組，不拼接故障前後的局部資料；成功樣本在前後都檢查保護狀態。持物交易出現終止性通訊失敗仍保留 pending 與停止狀態。假 SDK、真實 Robot/PWM 流程的 121 項相關回歸測試通過；實機是否消除該次逾時造成的中斷，另以後續驗證紀錄為準。

## 本機設定

提供者金鑰由伺服器環境讀取，正式變數為 `TYPESAFE_API_KEY`，相容別名為 `JEV_API_KEY`。本機啟動會載入專案的 `.env.local`；只有這兩個變數可被載入，檔案不會當 shell 程式執行，已存在的環境變數優先。

設定格式參考專案根目錄的 `.env.example`；真實值只放本機 `.env.local`，該檔目前權限為 `0600` 且已被 Git 忽略。不要把值放進前端、版本庫、範例檔或操作紀錄。缺少設定時 Jev 回報不可用，文字分類改用 Astra，退讓沿用原本候選選擇流程。狀態中的 `available` 只代表有設定有效格式的金鑰，實際連線結果要看 `error`；不代表提供者目前可達。

## 驗證到哪裡

2026-09-23 較早完成一次真實官方 API 的連線測試，輸入是人工建立、預先列出合格選項的合成狀態，沒有相機或硬體動作：

| 項目 | 實際回應 |
| --- | --- |
| 模型 | `jev-1.13.0` |
| 選擇 | `raise` |
| confidence | 0.86 |
| 該選項 probability | 0.91 |
| 這次端到端等待時間 | 約 703.334 ms |
| 輸入／輸出 token | 491／41 |

不含金鑰的原始回報保存在未納入 Git 的 `.runtime/jev-live-smoke.json`。這證明實際 API 與本機解析流程可互通，不能據此宣稱持續 2.5 Hz、機器人較快、更會避障或成功揮手。單次延遲不是穩定吞吐量測試。

同日上午的網頁實測輸入「跟我揮揮手」，Jev 約 440 ms 回報 HTTP 錯誤，Astra 約 11.3 秒完成文字分類，成功顯示揮手推薦卡，手臂仍未連線、沒有移動。這段回報保存在 `.runtime/day-search-suggestion.json`。後續一次僅含虛構選項的文字診斷確認是 **HTTP 403／Cloudflare 1010（`browser_signature_banned`）**，約 335 ms 返回；這是提供者存取封鎖，不是已確認的 JSON schema 問題。程式把此情況記為固定代碼 `provider_access_denied`，保留 Astra 回退，不自動重試或偽裝瀏覽器繞過封鎖。目前不能宣稱 Jev 快速分類已在此網路恢復正常。

冷啟動連線、保留保持目標、推薦卡不觸發動作、停止／持有／取消分支均有假通訊與假模型回歸測試。先前夜間因 `too_dark` 未能執行的動作，以及新增技能的完整實機結果，仍應逐項參照 [9 月 23 日驗證](LIVE_VALIDATION_2026-09-23.md)；文字推薦成功或測試通過不能代替完整揮手、抓取的實機驗證。
